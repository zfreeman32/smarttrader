Fill ordering is composition-dependent (`incremental_engine.py:361-367`, `:962-968`):

- If every manifest in an engine is an XGB model whose ID starts with `frvp_`/`ict_`, NaN is preserved, so the frozen imputer applies. All 11 ES roster models qualify.
- If an ES engine contains any other model (for example reserve ID 1, a TCN), `ffill().fillna(0)` runs after the contract check. The frozen fills (15–51 nonzero per ES model) are then never applied.
- EURUSD fills `ffill().fillna(0)` inside the builder. Every EURUSD frozen fill is 0, and the offline EURUSD features were also built with `fillna_numeric=True`.

The group composition used in B6 is therefore part of the parity contract.

**Scoring cadence.** The app scores every evaluated bar for every warm model: these are all-bar raw scores. Each score is stored as a prediction with a threshold decision. Route matching then gates the setup-family and pooled decisions. Offline, routes resolve on detector-selected same-side setups (ES) or on OTE events whose confirmation is the decision-bar close (EURUSD). IDs 22 and 26: their saved held-out predictions exclude every reversal confirmation bar, because their training rows exclude those bars (section 3 prompt 5). The app still scores those bars. Section 3 prompt 6 authorized runner scores there, but they are not comparable with saved predictions. In section 4 they are compared app-vs-reference (P layer) and never against saved predictions.

**Restart.** `warm_from_store` (`signals.py:386`, multi-group `:1409`) loads the last `runtime_history_bars` canonical bars with no evaluation, then resumes at bars after `last_processed_timestamp`. Feature seed offsets (`seed_state.py`) apply only to additive cumulative features, and no roster model selects one. The setup revision cursor is restart-safe (A5). The FRVP paper ledger restores its last emitted row.

**Reconnect / backfill / revision (A4).** IBKR callbacks carry version, completion, feed and first/last observation. `source_bar_history` is append-only, and canonical rows are upserted. The gap detector and backfill connector recover gaps, and ES gap recovery requires complete bars. On the model path, three behaviors are untested hypotheses for the fault-injection scenarios:

- `_fetch_signal_bars_after` only reads bars after the cursor, so a backfill behind the cursor never reaches the in-memory engine window.
- `FeatureRuntimeState.ingest_bar` replaces only a same-timestamp latest bar and raises on out-of-order bars, so a revision to an earlier bar is never re-ingested before a restart.
- `setup_revisions.py` re-runs detectors on corrections (≤128 prefix evaluations per call) "without rerunning trades". Model predictions are not recomputed.

**Gap / closure / roll.**

- The engine has no clock awareness. It consumes consecutive observed bars, matching the frozen `consecutive_observed_source_bars_v1` history contract ("availability, scheduled gaps, closures and rolls are separate gates").
- HTF buckets reject truncated, gappy, provisional and off-grid constituents (A3).
- The ES calendar is `es-dated-broker-hours-v2+weekly-diagnostic-fallback` (`market_calendar.py`). The app has no EURUSD calendar.
- Rolls are not back-adjusted. `contract_symbol` is carried on the bar. The ES training source is Databento `ES.v.0` with tagged roll fields, and the app records IBKR contract months (`roll_policy=cme_calendar`).

**Window size.** All 16 models resolve `runtime_history_bars = 8000`, because every model selects an `ict_*` feature (`infer_required_history_bars`).

## d. Offline reference on an arbitrary bar series

- **Historical windows (training-source bars).** The frozen reference already exists: `prepared/<target>/source_history.parquet` holds every consecutive source row's selected features (hash-pinned in the B4 v2 `source_history_contract`). Score it with the frozen production runner: `scripts.audit_b2_candidate_history.runtime` (ES) or `scripts.run_b2_ote_candidate_history.runtime_model` (EURUSD), on `history.iloc[end-context:end+1]`, as `scripts/run_section3_smoke_replay.py:485` does. No recomputation is needed.
- **Recorded live windows (no prepared rows).** Recompute with the repaired pipeline:
  1. Run `FeatureDatasetBuilder` with the frozen dataset config (`dataset.metadata.json` → `config`; `fillna_numeric=False` for ES, `True` with `drop_warmup_rows` for OTE) on the full contiguous series, not a bounded window.
  2. Apply the frozen transforms and selection.
  3. Run the same runner.
- **Anchor check before use.** Run the recompute path on historical windows and compare it with the frozen `source_history.parquet`. Any difference is producer drift since the July/May builds and B2 repair, classified before any live comparison.

## e. Why 2026-09-29 was `not_run_resource_bounded`, and the fix

`app_engine_audit` (`scripts/audit_b5_b6_live_feature_parity.py:415`) returns the stub before any work. The cost driver is real:

- the app rebuilds every feature set on 8,000 bars at every bar;
- `frvp_context` alone takes ~21 s per 9,000-row build (measured here, `attrib_es.json` timings), and ICT/HTF sets take ~1 s;
- the audit ran one engine per candidate across thousands of snapshot bars.

The fix:

1. One shared producer pass per stream per window. A stream-union engine computes producers once and selects per model; composition invariance is proven separately.
2. Bounded scenario windows instead of the whole archive.
3. Per-build timing measured first, with chunks sized to it.
4. Background, checkpointed runs with per-window completion markers.
5. Comparison of stored chunks offline with hashes and summaries only.
